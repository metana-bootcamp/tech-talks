Tempo Transactions

The Native Transaction Type

Welcome. Today we focus on Tempo Transactions. This is the native transaction type on Tempo and one of the most important developer-facing primitives. The official guidance is clear: if you are building on Tempo, you should strongly prefer Tempo Transactions over classic Ethereum transactions.

What Is a Tempo Transaction?

  • A new EIP-2718 transaction type
  • Type byte: 0x76
  • Available only on Tempo
  • Designed specifically for payment and application workflows
Tempo Transactions are not an application-layer abstraction. They are a protocol-native transaction type. This is why they can offer capabilities that are difficult or inefficient to replicate with standard Ethereum transactions alone.

Why They Exist

Classic Ethereum transactions were not designed
with modern payment UX in mind.

  • Fee token flexibility
  • Sponsorship
  • Batching
  • Parallelism
  • Delegation and scheduling
Many of the features people want for payment applications — sponsorship, batching, better nonce handling, scheduled execution — usually require additional infrastructure such as bundlers or paymasters on other chains. Tempo folds the most important of these capabilities into the transaction type itself.

Core Capabilities

  1. Configurable fee tokens
  2. Fee sponsorship
  3. Batch calls
  4. Concurrent nonces
  5. Access keys
  6. Scheduled transactions
We will walk through each of these capabilities. Together they explain why Tempo Transactions are the recommended default for serious development on the network.

1. Configurable Fee Tokens

flowchart LR User[User selects fee token] --> Tx[Tempo Transaction] Tx --> AMM[Fee AMM] AMM --> Validator[Validator receives preferred token]

Any USD TIP-20 can be used as the fee token

In a Tempo Transaction you can specify which TIP-20 token should be used to pay fees. The Fee AMM handles conversion so the validator still receives the token it prefers. This is a direct extension of the “no native gas token” design.

2. Fee Sponsorship

flowchart LR User[User action] --> App[Application or sponsor] App --> Pays[Pays the fee] User --> Executes[Transaction executes]

Applications can cover gas so users do not need to hold fee tokens

Fee sponsorship is one of the highest-leverage features for user experience. An application or third party can pay the transaction fee on behalf of the user. This enables feeless flows from the user’s perspective and is especially valuable for agents and consumer applications.

3. Batch Calls

flowchart TB Tx[Single Tempo Transaction] Tx --> C1[Call 1] Tx --> C2[Call 2] Tx --> C3[Call 3]

Multiple calls can be executed together in one transaction

Batching reduces the number of separate transactions a user or agent must send. It improves atomicity, reduces overhead, and simplifies wallet interactions. This is natively supported rather than requiring an external multicall pattern in every case.

4. Concurrent Nonces

  • Classic accounts are limited by a single sequential nonce
  • Tempo Transactions support independent nonces
  • This enables true parallel transactions from the same account
Sequential nonces are a major bottleneck for high-throughput applications and agents. Concurrent nonces remove that bottleneck by allowing multiple independent transactions to be in flight at the same time from one account.

5. Access Keys

flowchart LR Master[Master account] --> Key[Access key] Key --> Scoped[Scoped permissions] Scoped --> Actions[Allowed actions only]

Delegate limited signing power without exposing the root key

Access keys allow an account to delegate limited transaction authority. This is useful for agents, session keys, automation, and least-privilege designs. Instead of handing over full control, you grant only the permissions that are required.

6. Scheduled Transactions

  • Transactions can be constrained to execute within a time window
  • Useful for automated payments and time-based workflows
  • Supported at the transaction layer rather than only via external keepers
Scheduling is another capability that payment systems frequently need. By supporting it at the transaction level, Tempo reduces reliance on external automation infrastructure for many common flows.

Relation to Other Approaches

  • EIP-4337 — account abstraction via bundlers and entry points
  • EIP-7702 — temporary code delegation for EOAs
  • Tempo Transactions — native transaction type with payment-oriented features built in
It is useful to understand the landscape. EIP-4337 and EIP-7702 solve related problems in the broader Ethereum ecosystem. Tempo Transactions take a different path by making the most important capabilities native to the chain’s transaction format. That is why the developer experience can be simpler for many payment use cases.

Why Prefer Tempo Transactions

flowchart TB TT[Tempo Transactions] TT --> A[Better fee UX] TT --> B[Sponsorship without extra infra] TT --> C[Batching and parallelism] TT --> D[Delegation and scheduling]

They are the intended default for serious Tempo development

The recommendation from the protocol side is not subtle. If you are integrating with Tempo, you should plan around Tempo Transactions rather than treating classic Ethereum transactions as the primary path.

Developer Perspective

  • SDKs exist for TypeScript, Rust, Go, Python, and Foundry-oriented workflows
  • Integration is intentionally designed to be fast
  • Once adopted, many UX patterns become much simpler
From a practical standpoint, the important shift is mental as much as technical. Once your application thinks in terms of Tempo Transactions, features such as sponsorship and batching stop feeling like special cases.

How This Connects

flowchart LR TIP20[TIP-20] --> Fees[Fee tokens] Fees --> TT[Tempo Transactions] TT --> Lanes[Payment lanes] TT --> UX[Payment and agent UX]

TIP-20 and Tempo Transactions work together

TIP-20 provides the token and fee substrate. Tempo Transactions provide the execution vehicle that makes advanced payment flows practical. Together they form the core developer surface of the chain.

Mental Model

Classic transactions give you the baseline EVM model.

Tempo Transactions give you the payment-native model.

Hold on to that distinction. When we later discuss application patterns, agent flows, and sponsorship, the conversation will assume Tempo Transactions as the default tool.
