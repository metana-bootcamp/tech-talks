Tooling & Production Patterns

How you actually build on Tempo

Protocol knowledge is not enough to ship. This session maps the surfaces you will actually touch: SDKs, Foundry, RPC, TIDX, Tempo API, CLI, relays, and the failure modes that show up in production.

What You Should Leave With

  • Which client to pick for app, contract, agent, and infra work
  • How to send Tempo Transactions from Foundry and SDKs
  • When to use RPC vs TIDX vs Tempo API vs webhooks
  • How fee sponsorship looks in a real backend
  • What breaks if you treat Tempo like plain Ethereum tooling
Audience already knows Foundry, viem, and JSON-RPC. The value is the Tempo-specific flags, indexes, and operational patterns — not “here is what an SDK is.”

Tool Map

flowchart TB App[App / Agent] --> SDK[TS / Go / Rust / Python SDK] App --> CLI[tempo wallet / tempo request] Contracts[Contracts] --> Foundry[forge / cast / anvil] Backend[Backend] --> API[Tempo API + webhooks] Backend --> Relay[Fee payer / relay] Read[Reads] --> RPC[JSON-RPC] Read --> TIDX[TIDX SQL indexer]

Pick the plane that matches the job. Do not force one tool to do all of them.

A common anti-pattern is using only eth_getLogs for product reads, or using the explorer mental model for agent payments. Split write path, chain read path, product read path, and sponsorship path.

SDKs

All of them exist to speak Tempo Transactions: fee token, sponsorship, batching, access keys, 2D nonces. If a library can only send type-2 Ethereum txs, it is incomplete for production Tempo.

TypeScript Is the Default App Path

  • viem Tempo actions for transfers, DEX, fees, zones
  • wagmi hooks where you already have a React app
  • Prool for pooled local Tempo nodes in tests
For bootcamp and most product teams, start here. The important habit: use the Tempo actions, not a generic sendTransaction that forgets feeToken and then silently falls back to pathUSD assumptions.

Foundry Is First-Class

curl -L https://foundry.paradigm.xyz | bash
foundryup
forge init -n tempo my-project
  • Latest Foundry release includes Tempo support in forge, cast, anvil, chisel
  • Do not stay on an old nightly that only knows type-2 txs
Foundry is maintained by the same broader ecosystem that built Reth, which Tempo runs on. Students who already use forge test should keep using it. The new work is flags and precompiles, not a new framework.

Foundry Flags You Will Actually Use

--tempo.fee-token <ADDRESS>
--tempo.nonce-key <KEY>
--tempo.expiring-nonce
--tempo.valid-before <TS>
--tempo.valid-after <TS>
fee-token is the one everyone forgets on day one. nonce-key is how you submit parallel txs from one account. valid-before / valid-after are how scheduled / time-bounded Tempo Transactions show up in scripts. Walk one cast erc20 transfer with --tempo.fee-token live if you can.

SignatureVerifier Precompile

  • One interface for secp256k1, P256, and WebAuthn
  • You do not deploy your own verifier for passkeys
  • Foundry template includes a relayed-mail example
This connects back to Tempo Transactions and access keys. If you are verifying user or agent signatures onchain, start at the precompile instead of copying an OpenZeppelin-only ECDSA helper and then discovering WebAuthn does not fit.

JSON-RPC Is Still There

  • Standard eth_* methods work
  • Mainnet RPC: https://rpc.tempo.xyz
  • Plus Tempo namespaces for fork schedule and node admin
  • Zone RPCs are a different animal — authenticated and account-scoped
Do not tell students “just use the same RPC habits everywhere.” Public Mainnet RPC is Ethereum-shaped. Zone RPC requires X-Authorization-Token and will not give you global logs.

TIDX — Do Not Build a Private Indexer First

  • Hosted SQL indexer from Tempo Labs
  • Postgres for point lookups, ClickHouse for analytics
  • Mainnet: https://indexer.tempo.xyz
  • Testnet: https://indexer.testnet.tempo.xyz
  • Unauthenticated, read-only, CORS-enabled
Use TIDX for blocks, txs, logs, holders, decoded events. Running your own tidx is available when you need custom materialized views or stricter SLA. Product teams should not start by writing an eth_getLogs crawler for TIP-20 memos.

RPC vs TIDX vs Tempo API

NeedUse
Submit tx / read latest stateRPC
Historical txs, holders, decoded eventsTIDX
Payments product: activity, quotes, sponsorshipTempo API
Notify your backend of payment eventsWebhooks
This table is the operational core of the talk. If a student indexes payments by polling explorer HTML, stop them. If they use webhooks as the only source of truth with no chain check, also stop them.

Tempo API and Webhooks

  • Read payment activity without assembling raw logs yourself
  • Quote funding and exchange routes
  • Fee sponsorship / fee-payer flows
  • Organization webhooks for payment activity
Treat API + webhooks as a convenience layer over the protocol, not as a second ledger. Production pattern: webhook wakes the worker, worker verifies against RPC or TIDX, then you credit the user.

Fee Sponsorship in Production

flowchart LR User[User / Agent] --> App[Your app] App --> Relay[Relay / fee payer] Relay --> Chain[Tempo tx with feePayer] User --> Call[Calldata / intent]

User signs the action. Sponsor pays the fee token.

Server utilities exist specifically for relay and fee-payer handlers. You need policy on who you sponsor, rate limits, and which fee token the sponsor holds. Blind sponsorship is a drain. Targeted sponsorship is the product.

Tempo CLI

curl -fsSL https://tempo.xyz/install | bash
tempo wallet
tempo request
tempo node
tempo download
  • wallet — balances, funding, access keys, discovery
  • request — curl-like HTTP with MPP negotiation
  • node / download — run or snapshot-sync a node
For this session, CLI is the operator and agent surface. tempo request is the bridge into MPP, which is the next part of the series. tempo node is for people who need their own RPC, not for class-one “send a payment.”

Wallet CLI for Agents

  • Passkey-based Tempo Wallet from the terminal
  • Spend controls and service discovery
  • Designed so an agent can pay without holding a raw key in the prompt
Preview the MPP half of the course here without teaching the protocol yet. Agents need a wallet with limits more than they need another SDK method.

Local Testing

  • Foundry anvil with Tempo features
  • Prool: pooled Tempo node instances in TypeScript tests
  • Moderato testnet + faucet for integration tests
Unit-test contracts locally. Integration-test payments against testnet when you need real TIP-20, DEX, or zone queues. Do not pretend anvil is a full substitute for zone proving or hosted TIDX schemas.

Production Footguns

  • Sending type-2 txs and then wondering why fee-token UX is bad
  • Assuming one sequential nonce is enough for agent traffic
  • Indexing only ERC-20 Transfer and missing memos / DEX internal balances
  • Treating Zone RPC like public Mainnet RPC
  • Trusting webhooks without a chain check
  • Sponsoring fees with no budget or allowlist
Each of these maps to a previous talk. That is the point of putting tooling after protocol. Students should now hear “internal DEX balance” or “zone auth token” and know why it matters.

Recommended Default Stack

  1. TypeScript + viem Tempo actions for the product
  2. Foundry for contracts and scripts
  3. TIDX for historical reads
  4. Tempo API + webhooks for payment ops
  5. Relay only where you need feeless UX
  6. CLI for agents and incident debugging
You can swap languages. Do not swap away Tempo Transactions or a real index.

Mental Model

Protocol primitives are useless if the client still speaks vanilla Ethereum.

Use Tempo-aware writes, indexed reads, and explicit sponsorship.
