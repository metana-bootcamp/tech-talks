TIP-403

Policies, Compliance & Receive Controls

Welcome. Today we study the policy system on Tempo. TIP-403 is how the protocol attaches access control and compliance rules to TIP-20 tokens — and later how individual accounts can control what they are willing to receive.

Why Policies Exist

Real stablecoins need more than mint and transfer.

  • Who is allowed to send?
  • Who is allowed to receive?
  • Which tokens should an account accept?
  • How do issuers enforce this consistently?
If every issuer implemented its own allowlist or denylist logic, behavior would fragment. Tempo solves this with a shared registry that tokens can inherit instead of reinventing.

What TIP-403 Is

  • A shared policy registry
  • Policies are created once and reused across tokens
  • TIP-20 tokens check the registry on transfers
  • Registry address: 0x403c0000…0000
The key design choice is reuse. A policy is an object with an ID, a type, an admin, and a set of addresses. Multiple TIP-20 tokens can point at the same policy.

Two Layers of Control

flowchart TB Token[TIP-20 token policy] --> Check1[Can this sender and recipient use the token?] Account[Account receive policy] --> Check2[Does this receiver want this token and sender?] Check1 --> Check2

Token policy runs first. Receive policy runs after.

Keep these two layers separate in your head. The token policy is issuer-controlled compliance. The receive policy is receiver-controlled preference. They solve different problems.

Policy Types

  • Whitelist — only listed addresses may transfer
  • Blacklist — listed addresses are blocked
  • Compound — more advanced combinations exist at the protocol level, but they are not valid for receive policies
For teaching and most application work, start with whitelist and blacklist. Those two cover the majority of issuer compliance patterns.

Built-in Policies

  • policyId = 0 — always reject
  • policyId = 1 — always allow
  • Custom policies start at policyId = 2
These two built-ins are important defaults. Policy 1 is the open case. Policy 0 is the fully closed case. Custom policies are created from 2 onward.

How a Token Uses a Policy

flowchart LR Admin["Token admin"] --> Bind["Bind policyId to TIP-20"] Tx["Transfer or mint"] --> Check["isAuthorized(sender, recipient)"] Check -->|"pass"| Pass["Transfer proceeds"] Check -->|"fail"| Fail["Call reverts"]

Token-level policy failure reverts the call

The token stores the current policy ID. On transfer, it checks both sender and recipient against that policy. If either fails, the call reverts. Only the token admin can change which policy the token uses.

Receive Policies

An account can define what it is willing to accept.

  • Which senders may send to it
  • Which TIP-20 tokens it accepts
  • Who can recover funds if a transfer is held
This is the T6-era capability and it is easy to confuse with token policy. Receive policies belong to the receiving address, not to the token issuer. A regulated entity, a treasury, or a user can refuse unwanted deposits.

Receive Policy Shape

ReceivePolicy(account) = (
  senderPolicyId,
  tokenFilterId,
  recoveryAuthority
)

Sender and token filters must be built-in 0/1 or a simple whitelist or blacklist.

Three fields. senderPolicyId controls who can send. tokenFilterId controls which tokens are accepted. recoveryAuthority controls who can later claim blocked receipts.

What Happens When a Receive Policy Blocks

flowchart TB Send[Sender submits transfer or mint] --> TokenCheck[Token TIP-403 check] TokenCheck -->|fail| Revert[Revert] TokenCheck -->|pass| RecvCheck[Receive policy check] RecvCheck -->|pass| Credit[Funds credited normally] RecvCheck -->|fail| Guard[ReceivePolicyGuard holds funds]

Blocked inbound funds are held, not silently lost

This is a crucial behavioral difference. Token-policy failure reverts. Receive-policy failure does not revert the whole call. Delivery is redirected to ReceivePolicyGuard and a receipt is recorded so the funds can be recovered or rerouted later.

ReceivePolicyGuard

  • Protocol precompile at 0xB10C0000…0000
  • Records a receipt for each blocked transfer or mint
  • Recovery authority can later claim or reroute
Think of it as a holding area for unwanted inbound value. The sender does not need to know about the receiver’s policy in advance. If the send is blocked, the protocol preserves the funds instead of reverting or burning them.

Enforcement Order

  1. Token TIP-403 policy runs first
  2. If that fails, the transaction reverts
  3. If it passes, the receiver’s receive policy is checked
  4. If that fails, funds go to the guard
Repeat this order until it is automatic. Issuer rules are hard constraints. Receiver rules are acceptance preferences with a recovery path.

When to Use Which

  • Token policy — issuer compliance, KYC’d counterparties, sanctioned-address blocking
  • Receive policy — treasury only accepts certain tokens, account rejects unknown senders, regulated receiver constraints
If the issuer must prevent a transfer from happening at all, use a token policy. If the receiver simply does not want the incoming asset or sender, use a receive policy.

Implications for Developers

  • Do not assume every transfer credits the recipient immediately
  • Index guard receipts if you operate wallets or payment systems
  • Warn users when a send is likely to be held
  • Reuse policies instead of embedding custom allowlists in every token
For app builders this is operational, not just theoretical. Explorers, wallets, and payment processors should understand both revert cases and held-receipt cases.

Mental Model

TIP-20 moves value.

TIP-403 decides whether that movement is allowed.

Receive policies decide whether the destination wants it.

That is the complete picture. Token standard, then issuer policy, then receiver preference.
