Enshrined Stablecoin DEX

Protocol-native orderbook for TIP-20 interoperability

This session is for developers who already understand EVM orderbooks, AMMs, and token standards. We are not covering “what is a DEX.” We are covering why Tempo put an orderbook in the protocol, how it actually works, and what you must get right when integrating it.

What You Should Leave With

  • Why this is an enshrined orderbook, not Uniswap-in-a-precompile
  • How quote-token routing creates a single path between any two USD TIP-20s
  • Exact order types, escrow, matching, and flip semantics
  • How TIP-403 still gates makers, takers, and the DEX itself
  • Which APIs to call, what can revert, and what fails silently
If someone already knows how to integrate a Uniswap pool, this session should still be worth their time because the primitive is different: ticks, quote-token trees, flip orders, internal balances, and policy-aware trading.

The Design Constraint

Payments need cheap conversion between USD stablecoins.

  • Many issuers, one currency unit
  • Fragmented pairs destroy liquidity
  • Application-level routers add failure modes
Tempo assumes a world of many USD stablecoins, not one canonical dollar token. If every pair is a separate pool, liquidity fragments and routing becomes a product problem. The protocol instead forces a tree of quote relationships so there is one path between any two tokens.

Contract Surface

  • Singleton precompile: 0xdec0000000000000000000000000000000000000
  • USD TIP-20 to USD TIP-20 only
  • Onchain orderbook with price-time priority
  • No per-pair contract deployment
Treat this like a system contract, similar in status to the TIP-20 factory or Fee Manager. You do not deploy a pool. You create a pair against the token’s quote token and then place or take liquidity.

This is the most important disambiguation in the session. If you are swapping user value, you are on the DEX. If you are paying gas in a non-validator token, you are on the Fee AMM. They share the “stablecoin conversion” vibe and almost nothing else.

Quote Tokens Form a Tree

flowchart TB P[pathUSD
no quote token] A[USDX] --> P B[USDY] --> P C[USDZ] --> A

One quote per token. One route between any two tokens.

Each TIP-20 declares exactly one quote token. pathUSD is the optional neutral root: first deployed USD token, no quote of its own, fallback fee token. USDX to USDY routes USDX → pathUSD → USDY in one transaction. That is deliberate. It concentrates liquidity instead of creating an NXN pair matrix.

Why the Tree Matters

  • Routing is deterministic — no competing paths
  • Thin pairs still connect through shared quote liquidity
  • Cross-stablecoin payments can be atomic
  • Users and merchants need not hold the intermediate token
Walk a payment example. Alice holds USDX. Merchant wants USDY. Market makers quote both against pathUSD. One swapExactAmountIn can traverse both hops. Alice never intended to hold pathUSD. It is routing infrastructure.

Creating a Pair

createPair(address base)
  • Pair is always base against base.quoteToken()
  • Reverts if the token is not USD-denominated
  • Reverts if the pair already exists
  • Pair key is order-independent: pairKey(A, B)
You do not pass both tokens. The quote is metadata on the TIP-20. That is how the protocol keeps the graph a tree instead of letting apps invent arbitrary pairs.

Price Grid

  • PRICE_SCALE = 100_000
  • TICK_SPACING = 10 → 1 bp grid
  • MIN_TICK = -2000, MAX_TICK = 2000 → ±2%
  • Tick must be divisible by 10
  • Example: $1.0000 → 0, $0.9990 → -10, $1.0010 → 10
This is a tight band by design. These are USD stablecoins. A ±2% book is the relevant market, not a 50% AMM range. If you try to place off-grid or out-of-range ticks, placement reverts.

Book Structure

flowchart TB Pair[Pair] --> Bids[Bid ticks] Pair --> Asks[Ask ticks] Bids --> Q1[FIFO queue at tick] Asks --> Q2[FIFO queue at tick]

Bitmaps find live ticks. Queues are FIFO inside a tick.

Internally this looks more like a concentrated-liquidity tick bitmap plus a classic CLOB queue than like x*y=k. Each pair tracks bestBidTick and bestAskTick. A tick de-initializes when its liquidity hits zero.

Three Order Behaviors

TypeWhen it executesWhat it leaves behind
Swap / marketImmediatelyNothing resting
LimitWhen matchedResting order until fill or cancel
FlipWhen matchedSame orderId rewritten on the other side
Developers should choose based on intent. Taker flow: swap. Passive one-sided quote: limit. Standing two-sided convertibility: flip.

Limit Placement and Escrow

place(token, amount, isBid, tick) → orderId
  • Bid escrows quote at the tick price
  • Ask escrows base
  • Prefers internal DEX balance, then transferFrom
  • Enqueued FIFO at that tick
Escrow is the part people miss. A bid is not “I hope to buy later with wallet funds.” The quote is locked now. Cancel returns escrow to the maker’s internal balance.

Flip Semantics

placeFlip(token, amount, isBid, tick, flipTick) → orderId
  • Acts as a normal resting order until fully filled
  • Then rewritten in place at flipTick
  • Same orderId — it does not consume a new ID
  • Bids: flipTick >= tick; asks: flipTick <= tick
  • Same-tick flips are valid
Same-tick flips are the issuer convertibility trick. Place both sides at tick 0 and the book keeps offering 1:1-ish convertibility as fills flip back and forth. Flip emits OrderFlipped, not OrderPlaced.

Silent Failure on Flip Funding

flowchart TB Fill[Full fill] --> Bal{Internal balance
enough?} Bal -->|yes| Flip[Rewrite on
other side] Bal -->|no| Stop[No flip]

No transferFrom fallback on flip. This is easy to miss.

Initial placement can pull from the wallet. A later flip cannot. If the maker withdrew credits or never left enough internal balance, the order dies instead of flipping. If you are building an LP bot, this is a production bug waiting to happen.

Swap APIs

swapExactAmountIn(tokenIn, tokenOut, amountIn, minAmountOut)
swapExactAmountOut(tokenIn, tokenOut, amountOut, maxAmountIn)
quoteSwapExactAmountIn(...)
quoteSwapExactAmountOut(...)
Always quote first in production UIs and agents. Quote functions are view simulations and revert on insufficient liquidity. Then submit the swap with an explicit slippage bound.

Swap Execution Path

  1. Read caller’s internal DEX balance
  2. Pull wallet shortfall if needed
  3. If no direct pair, walk the unique quote-token path
  4. Consume book in price-time priority
  5. Credit makers internally at tick price
  6. Revert on slippage or missing liquidity
  7. Send output to the taker
Multi-hop is protocol routing, not an external aggregator. Because the quote graph is a tree, the path is unique. That removes a class of router bugs, but it also means a missing hop is a hard failure, not “try another route.”

Gas Scales With Book Work

  • Base cost: setup and token movement
  • Per order filled
  • Per tick crossed
  • Per flip triggered

Large size through a thin book is expensive. That is expected.

Do not promise constant-gas swaps. If an agent or payment flow must stay inside a tight gas budget, quote first and cap the size or require deeper books.

Internal Balances Are Part of the Protocol

balanceOf(user, token)
withdraw(token, amount)
  • Fills credit the maker internally
  • Later placements spend internal balance first
  • Withdraw is explicit
If you index only ERC-20 Transfer events you will mis-account LPs. Maker proceeds often never leave the DEX until withdraw. Wallet UIs that ignore internal balances will look like funds disappeared.

TIP-403 on the Book

flowchart TB Place[place / placeFlip / swap] --> M[Maker authorized
on base and quote?] M --> D[DEX contract authorized
by token policies?] D --> Ok[Proceed] M -->|no| Rev[Revert] D -->|no| Rev

Issuers can keep a token off the DEX entirely

The DEX is not a compliance bypass. Maker must be allowed to transfer both assets. The DEX address itself must be allowed by the token policy. That second check is how an issuer opts a token out of public trading.

Stale Orders

cancel(orderId)            // owner
cancelStaleOrder(orderId)  // anyone, iff maker is no longer authorized
  • If a maker gets blacklisted, their resting order can be cleaned up
  • Escrow returns to the maker’s internal balance
  • Reverts with ORDER_NOT_STALE if the maker is still authorized
This is the cleanup hatch for compliance changes after placement. Permissionless cancel is not a griefing tool against valid makers. It only works when TIP-403 now forbids the maker.

Events You Should Index

PairCreated(key, base, quote)
OrderPlaced(orderId, maker, token, amount, isBid, tick, isFlipOrder, flipTick)
OrderFlipped(orderId, maker, token, amount, isBid, tick, flipTick)
OrderFilled(orderId, maker, taker, amountFilled, partialFill)
OrderCancelled(orderId)
If you are building an indexer, explorer, or LP dashboard, OrderFlipped is mandatory. Treating a flip as a cancel-plus-new-place will break order identity and PnL.

Integration Checklist

  1. Know the token’s quote token before you assume a pair exists
  2. Quote, then swap with slippage bounds
  3. Track internal balances, not only wallet balances
  4. Leave inventory on the DEX if you want flips to keep working
  5. Handle policy reverts and stale-order cleanup
  6. Never use the Fee AMM as a trading venue
This is the practical close. A correct integration looks boring: quote, bound, account internally, respect policy. Most bugs come from treating this like an ERC-20 AMM pool.
