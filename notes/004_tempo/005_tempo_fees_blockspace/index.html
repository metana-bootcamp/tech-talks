Fees, Blockspace & Payment Lanes

How Tempo keeps payments cheap and predictable

Welcome. So far we have covered the mental model, getting started, TIP-20, and Tempo Transactions. Today we open the fee system and the blockspace design. These two areas explain why payments on Tempo stay cheap and reliable even when the network is busy.

Why This Matters

On most chains, payments compete for the same blockspace
as complex DeFi, NFT mints, and heavy computation.

The result is unpredictable fees and delayed inclusion.

This is one of the core problems Tempo set out to solve. If payments can be crowded out, unit economics break and real payment systems become unreliable. The fee system and payment lanes are the protocol’s answer.

No Native Gas Token

  • There is no volatile native token used for gas
  • All fees are paid in USD-denominated TIP-20 stablecoins
  • This keeps costs predictable and accounting simple
This decision cascades through the entire fee design. Users and applications never need to acquire a separate speculative asset just to interact with the network.

High-Level Fee Flow

flowchart LR User[User selects
USD TIP-20] --> Tx[Transaction] Tx --> AMM[Fee AMM] AMM --> Val[Validator receives
preferred token]

The Fee AMM converts between stablecoins automatically

The user (or fee payer) chooses a USD TIP-20 token. The Fee AMM converts it into the token the current validator prefers. From the user’s perspective the experience stays simple.

The Fee AMM

  • Protocol-native component
  • Provides liquidity for fee-token conversion
  • Fixed conversion rate of 0.9970 (0.3% to liquidity providers)
  • Insufficient liquidity makes the transaction invalid
The Fee AMM is not an optional application. It is part of the protocol and is what makes multi-stablecoin fee payment practical. Liquidity must exist for the chosen fee token; otherwise the transaction cannot proceed.

How the Fee Token Is Chosen

  1. Transaction-level fee_token (highest priority)
  2. Account-level default set by the fee payer
  3. Inferred from a TIP-20 transfer or certain DEX calls
  4. Fallback to pathUSD
The protocol has a clear order of precedence. Explicit choice at the transaction level always wins. If nothing is specified, sensible defaults still produce a working fee path.

Fee Sponsorship

flowchart LR User[User / Agent] --> Action[Performs action] Sponsor[Sponsor / App] --> Pays[Pays the fee] Action --> Executes[Transaction executes]

A third party can pay fees on behalf of the user

Fee sponsorship is a first-class capability. An application, relay, or other account can act as the fee payer. This is essential for feeless user experiences and for many agent flows.

Bounded Dynamic Base Fee

  • Base fee adjusts with network usage
  • Hard cap keeps costs predictable
  • Floor prevents fees from collapsing to zero in quiet periods
  • Example for a ~50k gas TIP-20 transfer:
    • Cap ≈ $0.0006
    • Quiet floor ≈ $0.00003
The base fee is dynamic but bounded. This combination gives the network a congestion signal while still protecting payment applications from extreme fee spikes.

Blockspace Design

Tempo extends the Ethereum block format
with explicit support for payment lanes.

  • Separate accounting for payment and non-payment capacity
  • System transactions for protocol operations (including the Fee AMM)
Blockspace is not treated as a single undifferentiated resource. The protocol deliberately partitions capacity so that payments retain guaranteed room.

Payment Lanes

flowchart TD subgraph Block["One Block"] PL["Payment Lane - Reserved capacity"] GL["General Lane - Other transactions"] end Pay["Payment transactions"] --> PL Other["Non-payment transactions"] --> GL

Payments receive dedicated blockspace by protocol rule

This is the central idea. A large portion of blockspace is reserved for payment transactions. Even under heavy general computation load, payments still have room and therefore more predictable fees and inclusion.

How a Transaction Is Classified

A transaction is treated as a payment when:

  • The recipient starts with the TIP-20 payment prefix, or
  • For Tempo Transactions, every top-level call targets a TIP-20 payment address

Classification uses only transaction data — no state lookup is required.

Classification is deliberately simple and data-driven. This keeps it efficient at the consensus layer and makes the rules easy to reason about. TIP-20 transfers that qualify automatically benefit from the payment lane.

Dual Gas Constraints

  • gas_limit — total capacity of the block
  • general_gas_limit — limit on non-payment transactions in the proposer lane

Non-payment transactions cannot consume the entire block. Payment capacity is protected.

Validators enforce both constraints. The total gas used must stay under the overall gas limit, and non-payment traffic in the proposer lane is further constrained by general_gas_limit. This is how the reservation is enforced.

What This Achieves

flowchart LR Lanes[Payment Lanes] --> Pred[Predictable inclusion] Fees[Bounded fees] --> Cost[Stable unit economics] Pred --> UX[Reliable payment UX] Cost --> UX

Together, lanes and fees produce payment-grade reliability

The combination is what matters. Reserved blockspace protects inclusion. Bounded stablecoin fees protect cost. Together they create the conditions real payment systems need.

Implications for Developers

  • Prefer TIP-20 transfers when you want payment-lane behavior
  • Use Tempo Transactions for sponsorship and flexible fee tokens
  • Do not assume general-purpose traffic will always leave room — the protocol already protects payments
  • Budget fees in stablecoin terms, not in a volatile native asset
From a builder’s perspective the rules are actionable. Structure value-moving flows as TIP-20 payments when possible. Use sponsorship when you want to abstract fees away from the end user or agent.

Mental Model

Fees are stablecoin-native and bounded.

Blockspace is partitioned so payments keep guaranteed capacity.

Payments are first-class at the protocol level.

This is the key takeaway. Tempo does not merely hope payments will be treated well under congestion. It encodes that preference into the fee system and the block structure itself.
